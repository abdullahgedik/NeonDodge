# Neon Dodge — Project Notes

A LÖVE2D (Lua) project the user is building specifically **to learn LÖVE and Lua**. Not a shipping product — every feature is chosen for what it teaches, so lean toward explaining/using idiomatic LÖVE patterns over the fastest hack. This file exists because the coding session this project was being developed in was rooted in an unrelated repo (`kensan_app`, a Flutter project) and couldn't be switched — start fresh sessions with this file's directory (`NeonDodge/`) as the actual working directory/root so tools resolve paths correctly.

**Claude Code sessions do not sync across the user's machines** (confirmed — session history is local/per-install, not account-synced even in the desktop app). This file is the actual continuity mechanism between machines/sessions: keep it current. See the last working agreement below.

**`README.md` is the other half of the documentation and has a different job.** This file is the *history*: why each decision was made, what was tried and reverted, which bugs recurred. `README.md` is the *map*, written for the user as a contributor: the frame lifecycle, a one-line-per-file module table, the four invariants that bite (Screen vs love.graphics, backward pool iteration, `hazard_*` collision helpers, `dt`), recipes for adding a hazard/boss/card, and a section explaining the Lua idioms this codebase leans on (forward declaration, table-as-namespace, named-args-via-table, `goto continue`). When a change alters how someone would *navigate or extend* the code, update README.md too — not just the history here.

## What the game is

Top-down dodge/collect arcade game. **The game is authored at a fixed 960x540 (16:9) and always will be** — every spawn bound, boss patrol amplitude, arena wall, blast radius and HUD position is tuned against those two numbers — but the *window* is freely resizable (default 1024x576, min 640x360, **F11** toggles fullscreen). `src/screen.lua` maps that play area onto the window, letterboxed to preserve 16:9 so nothing ever stretches or misaligns. Crucially it is **not** a 960x540 image stretched up: the scale transform is applied *before* the scene is drawn, so every shape rasterizes at the window's true resolution and stays crisp at any size — the whole game is procedural (rectangles, circles, polygons, lines; no sprites anywhere), so vector geometry has no native resolution to lose. Game logic asks `Screen.WIDTH`/`Screen.HEIGHT`, never `love.graphics.getWidth/getHeight` — see the `src/screen.lua` entry below for why that distinction matters.
- Player: cyan square. Move with WASD/arrows or a gamepad's left stick/d-pad. Shift or gamepad A dashes (0.1s burst, 0.75s cooldown, both tunable by cards) — **the player is a true phase-through while dashing**, not just damage-immune: every hazard's collision check (Enemy, ZigzagEnemy, Boss body, Boss laser, Projectile) skips entirely while `player.is_dashing`, so nothing gets destroyed/consumed and no FX/hitstop fires either, on top of `take_damage` itself short-circuiting to `"dodged"` as a defensive fallback. Orb/VoidOrb pickups are deliberately *not* phased — they're beneficial, so dashing through them still collects them. This is what makes the Quick Dash/Long Dash cards genuinely defensive tools, not just mobility.
- HP: 3 max by default, shown as hearts top-left. Max HP can change at runtime via cards (Vitality +1, Glass Cannon -1).
- Red triangles ("Enemy") fall from top → touching one costs 1 HP. Speed ramps +5 per miss, capped (`Enemy.max_speed`) so it can't run away unbounded.
- Orange/red-ish diamond ("ZigzagEnemy") — same damage rule and capped ramp as Enemy, but sine-waves horizontally while falling. Fill `(1, 0.4, 0.05)` with a dark red `(0.7, 0, 0)` outline for readability against the yellow orb.
- Yellow circles ("Orb") → +5 score. Every 5th orb: heals +1 HP if not at max HP, otherwise **grants a one-hit shield instead** (only if not already shielded). The "Orbs: X/5" HUD counter shows progress toward that next milestone (wraps every 5, showing 5/5 right at the trigger moment), not the lifetime total.
- Purple orbs ("VoidOrb") → +10 score on catch; **missing** one costs 1 HP (unless the Void Ward card is active); its fall speed is eased by the same "Slow Fall" card modifier as Enemy/ZigzagEnemy, since missing one has a real HP cost like touching a hazard does (Orb, a pure pickup with no downside, is deliberately not affected).
- Bronze/copper octagon ("Mine") — a genuinely different kind of hazard: the body itself is harmless, only its shockwave deals damage. Falls slowly, anchors in place at a random height, then arms: a growing warning ring appears at its blast radius immediately (so there's maximal time to route around it), and its core flashes hotter orange-red and faster as the ~1.3s telegraph runs out. On detonation, only a player still inside the blast radius (dash phase-through still applies) takes 1 HP, boss-tier shake (0.2/8, bigger than a normal hazard touch); the mine is removed either way. "Dodge the moving shape" vs. "be clear of this zone by the deadline" — the first hazard in the game that isn't a contact-on-touch threat.
- Shield: one-hit block, blue ring wrapping the player, quick pop-in animation then holds fixed size/alpha (no continuous pulsing).
- Boss: spawns every 6th wave (`BOSS_WAVE_INTERVAL` in `main.lua`), ~14s encounter then leaves on its own (game is pure-dodge, no player attack, so every boss is a survive-the-encounter set piece, not a fight). Touching a boss body costs 1 HP, gated by a hit-cooldown so overlap doesn't melt HP every frame. Surviving it awards bonus score and opens the card-select screen. Three deliberate breathers pace these transitions instead of snapping straight through them: a **"BOSS INCOMING" telegraph** (`BOSS_INCOMING_DELAY`, 1.6s — existing hazards keep falling but no new ones spawn, and a pulsing warning shows) before the boss actually appears; a **freeze-frame beat** (`POST_BOSS_PAUSE_DURATION`, 1.0s — the whole game visibly holds still) after the boss dies and before the card screen opens; and a **confirm hold** (`CARD_CONFIRM_DELAY`, 0.4s — the picked card stays highlighted, the other two dim) after choosing a card and before play actually resumes. **Nine distinct boss types cycle in a fixed escalating sequence** (`Boss.SEQUENCE` in `src/boss.lua`: sentinel → charger → homing → bomber → laser → phantom → splitter → warden → turret → repeats). The four newer types are deliberately *interleaved* rather than appended — tacked onto the end they'd sit behind five encounters (wave 36+) and effectively never be seen in a normal run:
  - **Sentinel** patrols horizontally (full screen width, see below) + fires a 7-shot downward spread every 0.95s, with a **35% chance** of a second volley 0.28s later rotated half a shot so it threads the first fan's gaps. The chance is random rather than every-time on purpose: a guaranteed double is just a denser fan you learn once, but a coin-flip means you can't commit to stepping into a gap the instant the first volley passes. Multiple attempts were made to stop players camping above it: a fixed upward fan (blocked by corners), then a shot tracking the player's real position (still trivially dodgeable as a single periodic projectile from a static spot) — both were dropped in favor of denying the position outright: it's bigger-bodied (90x60 → 125x75) and walls off the top of the screen entirely for the duration of the encounter (`Player.min_y`, drawn as a faint dashed line) so "stand above the boss" isn't a legal position at all.
  - **Homing** patrols slower and fires player-seeking projectiles every 1.45s (steering/vector-math exercise). Its shots **detonate in a 52px blast when their 6s lifetime runs out** rather than just vanishing, telegraphed by a growing green ring over the last 1.0s -- deliberately smaller than a Mine's 90 (that stays the dedicated zone-denial hazard) and telegraphed for the same reason a Mine is: an unwarned blast is a coin flip, not a dodge. This turns the type from "outrun the chasers" into "outrun them *and* don't be where they die", since a denser stream now steadily seeds the arena with delayed explosions. Any still-active homing shots are also explosion-cleared the instant the boss itself starts leaving, so its threat doesn't outlive it even within that 6s window. Also enforces the same `Player.min_y` top-of-screen wall as Sentinel/Splitter — its own shots steer continuously so coverage was never the issue, but a player parked far enough above still had time to read and juke each shot before it curved into range.
  - **Laser** fires noticeably faster now (0.6s between sweeps instead of 1.0, aimed shot every 0.75s instead of 1.0) while still exiting on exactly 4 sweeps -- 5 was tried and reverted, since with the shorter cooldown it pushed the encounter to ~23s against ~16s for every other type, which reads as dragging rather than intense. It barely moves but its beam does: a full-width **or** full-height band that sweeps edge-to-edge across the *entire* screen, randomly one of left→right / right→left / top→bottom / bottom→top each cycle (cooldown → telegraph → firing). Telegraph shows a single line at the start position only (an end-line too was tried and dropped — with a full edge-to-edge sweep the far end is always a screen edge, so showing it added confusion, not clarity). The encounter tracks completed sweeps directly (`laser_sweep_count`) and exits only once exactly 4 have finished, instead of sharing the generic per-type time budget — that budget didn't line up with the beam's own cycle length, so the boss could leave mid-telegraph or cut the last sweep off partway through. Also fires a straight (non-homing) aimed shot at the player on its own independent ~1s cadence, decoupled from the beam cycle so shots don't wait on it — this is the one place `fire_aimed_shot` is still used; Sentinel/Splitter's own aimed "guard" shots were removed once the `Player.min_y` wall made them redundant.
  - **Splitter** is small/fast and splits into two clones partway through its encounter (`is_splitter`/`split_time = 6`) — the original (85x55) patrols the full screen width and enforces the same top-of-screen `Player.min_y` wall as Sentinel for its whole encounter. **The two clones are no longer identical.** They used to be twin bouncers differing only by position, which made the split double the same spray pattern rather than change the fight; they now take asymmetric roles, randomized per split so the pairing can't be memorized: a **hunter** (`splitter_hunter`) that relentlessly closes on the player's column (`Movement.track`, a standalone version of the charger's aim-phase tracking with no telegraph or slam) and fires a fast aimed shot every 0.85s, and a **sentry** (`splitter_sentry`) that drifts in a small circle around the spot it split into (`Movement.orbit_local` — unlike Turret's orbit, centered on wherever it happens to land rather than a fixed arena point) and fires a full ring every 1.3s. Neither needs a `player_min_y` wall: `Attacks.aimed_shot` always targets wherever the player actually is, and a full ring has no directional blind spot, so — unlike the original splitter's fan — there's no position to structurally deny in the first place. The split moment itself also gained a ring-burst FX at the point of the split (there was previously none at all — one body vanishing and two smaller ones just being there read as a substitution, not an event).
  - **Turret** orbits in a circle around a fixed arena point (not stationary) and fires full-circle projectile rings that rotate their angle offset a little more each burst (a slow bullet-hell spiral) — rings per volley now **alternate 2, 3, 2, 3...** (`burst_counts`), each 0.18s apart and each rotated another half-step so they interleave into one dense lattice rather than repeating. The alternating count is what makes it readable but not memorizable: you can count rings as they arrive, but how many more are coming changes every volley, so the safe moment to cross a ring gap moves with it.
  - **Charger** is the only boss that fires *nothing* — its body is the entire attack. It tracks the player's column at a capped speed (closing the gap, never teleporting onto them), stops dead, telegraphs the full-height column it's about to fall through, then slams to the floor and climbs back up. **The whole cycle winds up as the encounter runs**: `charge_aggression` goes 0->1 over the encounter and `charge_movement` lerps all five knobs against it, so the last slams come with ~35% of the opening aim time, half the telegraph, and 1.55x the movement speeds. At a fixed rhythm it was too predictable -- early slams are still readable enough to learn the pattern on, but late ones give so little warning that you have to commit to moving *before* the telegraph appears. Standing still is the failure state, and dash phase-through is the clean answer, which makes it the sharpest test of the dash in the game. Enforces `Player.min_y` (175) — it only ever slams *downward*, so anything above its hover line is a position it structurally cannot threaten.
  - **Bomber** seeds the arena with real `Mine` hazards instead of shooting (via a `spawn_mine` callback into `main.lua` → `Mine.spawn_at`), so its bombs telegraph, explode and damage through the exact same path a wave-spawned mine does — boss-scale zone denial in a visual language the player already knows. One bomb per volley is dropped on the player's current position (punishing camping), the other scattered (keeping the whole arena live). It **also fires a 5-shot spread 0.5s after each bomb drop** -- deliberately offset rather than simultaneous, since mines are a "be elsewhere in a moment" threat and projectiles a "move now" one, and landing both on the same beat reads as one confusing wall; staggered, they're two problems that overlap, so you dodge the spread into ground the bombs already claimed. Also enforces `Player.min_y` (130), since bombs can't be seeded at the very top without overlapping the boss's own body.
  - **Warden** squeezes the legal play area itself: a slow ease-out shrink from the full screen down to a centered **320px**-wide arena whose top edge sits at y=235, reached over 70% of the encounter and held there. Generalizes the existing one-edge `Player.min_y` wall into all four edges. Tightened from 380/y=215/80%, since at the old numbers it finished barely narrower than the space a Sentinel already denies -- those three fields plus `fire_interval` (1.7 -> 1.15) are the knobs for the rework the user is considering. Its actual shots barely matter — the threat is that the room to dodge them keeps shrinking.
  - **Phantom** has no readable patrol at all: it holds position ~1.5s, fades out, reappears somewhere else in the upper arena, and fires the instant it lands. While anything but fully visible it's `intangible` — collision *and* firing both switch off, since a half-faded boss you can walk into (or that shoots from nowhere) reads as a bug. Blink positions are always ≥150px from the player, so it can't materialize on top of them for an unreactable hit. Each volley is **2-3 bursts of a 4-shot ring, alternating between axis-aligned (+) and diagonal (X)**, 0.22s apart, on a 0.65s fire interval. One 8-shot ring would cover every one of those directions at once -- denser, but completely static, with no moment where some directions are safe; alternating means the gaps move between bursts, so the answer to the first burst is the wrong place to stand for the second. It fires **rings** rather than a downward fan precisely because its position is unpredictable — a directional attack would be dodgeable by standing above wherever it happened to land, and the ring is what lets it skip the `player_min_y` wall every other top-threatened type needs.
- Debug spawns any boss on demand, independently of the real in-run sequence: **F3** steps to the next type in `Boss.SEQUENCE`, and **number keys 1-9** jump straight to a specific one (F3 alone meant nine presses to reach the last type, each replacing the previous mid-encounter, which made testing any single boss tedious). The overlay lists the whole roster with its hotkey number and marks which one F3 points at, and each live instance's sub-state shows alongside its enter/hover/exit phase — see `Boss.debug_summary`/`debug_state` below. Adding a boss type needs only `src/boss.lua` (the `BOSS_TYPES` registry plus `Boss.SEQUENCE`); both the wave cadence and every debug hotkey pick it up automatically.
- **Roguelike card system**: after every boss encounter, gameplay pauses and offers 3 of 20 cards (see `src/cards.lua`) — pick via mouse click, number keys 1/2/3, WASD/arrows + Enter/Space, or gamepad d-pad + A. Effects span survivability (+max HP, auto-shield/regen ticking, dodge chance, banked extra-life revives, Void Ward), score (flat bonuses, multipliers, low-HP double-score), mobility (move speed, dash cooldown/duration), and hazard-easing (fall speed, enemy speed-ramp, hitstop/shake intensity).
- Wave-based difficulty: spawn rates ramp over ~2 minutes via `src/difficulty.lua`; `Difficulty.wave()` drives both the boss cadence and the UI wave counter. Waves 1-3 are shorter than the steady-state 20s (10s/13s/16s) so the early game escalates noticeably faster instead of an uneventful sit before anything changes — wave 4 onward is a flat 20s.
- **Hazard storms**: every 3rd wave that *isn't* a boss wave (with `BOSS_WAVE_INTERVAL` a multiple of `STORM_WAVE_INTERVAL`, storms and bosses naturally alternate every 3 waves with no gaps), a ~1.2s telegraph warning plays (gameplay unchanged — the point is "brace yourself", unlike the boss telegraph's "things calm down"), then a 10s storm where one hazard's spawn rate roughly triples, before dropping back to normal. A storm is defined by which single hazard it **narrows down to**, not by piling everything on: every hazard *not* named in that storm type is suppressed outright for its duration. An early version sped up every type at once and was unsurvivable in practice — the fix was narrowing the mix, not tuning the multiplier down.
- **Four storm types**, each built around one hazard and each unlocking alongside it (`STORM_TYPES` in `main.lua`, gated on the same `unlock_stage` as the hazard roster), so the storm variety grows as the game does instead of every storm being the same event forever. Each storm rolls randomly from the types unlocked so far, never repeating the previous one back-to-back when there's a choice. The banner is named and colored by the type itself:
  - **HAZARD STORM** (always available) — Enemy + Orb ~3x. The original: a red-triangle flood with extra orb pickups as the reward for braving it.
  - **VOID RAIN** (with VoidOrb) — a purple downpour that inverts the game's core instinct: these must be *caught*, and missing one costs HP, so "dodge everything" is what kills you.
  - **CROSSFIRE** (with ZigzagEnemy) — weaving hazards only; reading sine paths instead of straight falls.
  - **MINEFIELD** (with Mine) — zone denial rather than dodging; the arena fills with blast circles and it's the safe space that keeps moving, not the hazards.
- **Progressive hazard unlocks**: instead of every hazard/pickup type being live from wave 1 with only their spawn *rate* ramping, the roster itself grows one event at a time. Only Enemy and Orb are ever active from the start; the first boss or storm to conclude unlocks VoidOrb, the second unlocks ZigzagEnemy, the third (and every one after) unlocks Mine. With the current 6/3 boss/storm cadence this lands as: waves 1-3 Enemy+Orb only, VoidOrb after the wave-3 storm, ZigzagEnemy after the wave-6 boss, Mine (full roster) after the wave-9 storm. Each new type's introduction rides on an event milestone that already exists, rather than adding a separate unlock timer.
- Screen-space shaders, always layered: bloom/glow (`src/bloom.lua`) on the whole scene, plus an on-hit chromatic-aberration + vignette pulse and an automatic red "heartbeat" vignette while at 1 HP (`src/hit_effect.lua`).
- Persistent high score via `love.filesystem` (`src/high_score.lua`), shown on the menu and game-over screens. The main menu's "Reset High Score" option won't fire on a single click — it *arms* (button turns red, label changes to "Click again to confirm") and needs a second confirm within 3s, disarming automatically on timeout or on navigating the cursor away, so a misclick can't silently erase the record.
- Debug mode (**F1** to toggle) — bottom-screen overlay of state/wave/boss/player HP/active card modifiers/owned cards. While enabled: **F2** forces a card-select screen, **F3** force-spawns the boss, **F4** skips a full wave forward, **F5** toggles god mode (no damage).
- Game states: `menu` → `playing` → `paused` (P, Escape, or gamepad Start) → `card_select` (after every boss) → `game_over` (R / gamepad A to restart). From `paused`, R/gamepad A also restarts and M/gamepad B quits straight back to `menu`, both without needing to die first — either path saves the in-progress score as a potential high score before discarding it, same fairness as a normal death. Escape is deliberately **not** wired to `love.event.quit()` anywhere except the main menu's own "Quit" option — early on it quit the whole game outright from any state, which is a jarring way to lose an in-progress run to a reflexive keypress; it's now just a second key for the same pause toggle P already does (including toggling back out of pause).
- **Main menu and pause are real navigable menus**, not just hint text: main menu offers "Start Game"/"Reset High Score"/"Quit", pause offers "Resume"/"Restart"/"Quit to Menu" — both drive-able by mouse click, keyboard (arrows/WASD + Enter/Space), or gamepad (d-pad + A), on top of the direct hotkeys/buttons above which still work unchanged as shortcuts. The cursor always defaults to the option matching the old single-key behavior (main menu → "Start Game", pause → "Resume"), so pressing Space/A with zero navigation reproduces exactly what used to happen.

## Architecture

Module-per-entity pattern in `src/`, each module is a table returned from its file, generally exposing `load/update/draw/pause/resume/reset`. Modules receive sibling modules as parameters where practical (e.g. `Enemy.update(dt, game_over, player, on_collision, spawn_rate)`); a few modules (`Cards`, `Debug`, `FXManager`) are `require`d directly by others since they're read-only "service" lookups rather than entities needing lifecycle wiring — this is an established, intentional exception, not drift to fix. Those direct requires are always **top-level locals** (`local FXManager = require("src/fx_manager")` at the head of the file), never re-required inside a function body — `fx_manager.lua` has no requires of its own, so there's no circular-dependency reason for the inline form.

- `main.lua` — owns score, orb count, screen-shake state, hit-stop timer, wave/boss/card trigger bookkeeping; wires modules together via callback functions passed into each module's `update`. Centralizes card-modifier application for anything that isn't naturally owned by one module (`love.shake`/`love.hitstop` multiply by `shake_mult`/`hitstop_mult`; `love.increase_score` applies `score_mult`/`low_hp_score_mult` and rounds to an integer — a fractional multiplier like Glass Cannon's 1.5x will otherwise leave float scores). Three transition timers pace the normal→boss→card-select→normal flow, all ticked in `love.update`: `boss_incoming_timer` (defers the actual `Boss.spawn` call, suppressing new hazard spawns via `suppress_spawns` in the meantime — existing hazards keep falling, only new spawns stop), `post_boss_pause_timer` (set by `on_boss_encounter_end` instead of calling `trigger_card_select` immediately; ticked with an early `return` right after the `hitstop_timer` check, the same "skip the rest of this frame" trick hitstop already uses, so the whole game visibly freezes for the duration), and `card_confirm_timer` (set by `choose_card` instead of resuming immediately, ticked inside the `CARD_SELECT` branch of `love.update`, calling `finish_card_select()` once it elapses). `trigger_card_select`/`finish_card_select` are **forward-declared** (`local trigger_card_select` etc. near the top of the file, assigned later without the `local` keyword) specifically so `love.update` — defined earlier in the file — can call them; Lua resolves `local` scope by textual position, not call order, so without the forward declaration `love.update` would see them as undefined globals. `trigger_card_select` defensively clears `post_boss_pause_timer`/`pending_card_select` on entry so it can't misbehave if reached a different way (e.g. debug F2) than the delayed path. Storm events (`storm_telegraph_timer`, `storm_timer`) are scheduled the same wave-transition way boss encounters are (`wave > last_storm_wave and wave % STORM_WAVE_INTERVAL == 0`), with an explicit `wave % BOSS_WAVE_INTERVAL ~= 0` guard so a storm can never land on a boss wave — the two systems are otherwise completely independent. All five hazards now resolve their spawn period through one `spawn_rate_for(kind, storm, suppressed, unlocked)` helper instead of five hand-written expressions; it returns `math.huge` ("never spawns") for all three suppression cases — boss encounter on screen, hazard not unlocked yet, or a storm running that this hazard isn't part of — and otherwise scales `Difficulty.spawn_rate(kind)` by the storm's own per-hazard multiplier. `STORM_TYPES` is the storm registry: each entry has an `id`/`name`/`color` (the banner names and colors itself from this), a `required_unlock_stage` keying it to the same counter that gates the hazard roster, and a `rates` table of per-hazard multipliers. Because those rates multiply a *period*, a value below 1 means "more often" (0.35 ≈ 3x) and 1 means "unchanged" — and any hazard **not listed is suppressed outright**, which is what makes a storm a narrowing rather than a pile-on. `pick_storm_type()` rolls from the unlocked types excluding the previous one (falling back to a repeat only when that leaves nothing, i.e. early on when swarm is the whole roster). `storm_type` is chosen at *telegraph* time, not when the storm starts, so the warning banner can name what's coming; spawn rates only actually change once `storm_timer > 0`. `src/difficulty.lua` itself is untouched either way — the ramp stays the ramp, storms are a `main.lua`-level event layered on top. A single `unlock_stage` counter (0-3, `UNLOCK_STAGE_VOID_ORB`/`_ZIGZAG`/`_MINE` mark the thresholds) gates whether VoidOrb/ZigzagEnemy/Mine are even eligible to spawn at all — each is forced to `math.huge` alongside the existing `suppress_spawns`/`storm_active` checks until `unlock_stage` reaches its threshold. It's incremented by exactly 1 (capped at `MAX_UNLOCK_STAGE`) from two places: `love.on_boss_encounter_end` and the `storm_timer` tick block the instant it crosses back to 0 — i.e. once an event *concludes*, not when it starts, matching "unlock the next thing after that boss/storm" rather than "at the start of it." `restart_game(target_state)` takes an optional target (defaults to `PLAYING`) so `quit_to_menu()` can reuse the exact same reset logic but land on `MENU` instead — it also unconditionally calls `HighScore.try_save(score)` and `love.resume()` before wiping state, neither of which the original GAME_OVER-only restart path needed (death already saves the score, and GAME_OVER was never reached via `love.pause()`), but both are required once restart/quit became reachable *from* `PAUSED`: skipping the resume would leave every module's `is_paused` flag stuck true, silently freezing the "fresh" run. `menu_cursor` is a single shared cursor variable for whichever simple menu (main menu or pause) is currently showing — only one is ever active at once, so one variable covers both; `toggle_pause`/`quit_to_menu` reset it to 1 on entry so a stale index from the *other* menu (which may have more or fewer options) can never carry over. `select_main_menu_option(index)`/`select_pause_menu_option(index)` are the dispatch tables mapping a menu index to an action, called from keyboard (arrows/WASD + Enter/Space), gamepad (d-pad + A), and mouse (`love.mousepressed`'s shared local `hit_index(x, y, rects)` helper, reused for card-select too) alike — every input path funnels through the same two functions so there's exactly one place each menu's behavior is defined. `reset_confirm_timer` (ticked only while `GameState.MENU`) implements the "Reset High Score" arm/confirm: `select_main_menu_option(2)` starts the timer on a first select and only calls `HighScore.reset()` if it's already running (a second select within the window); it's zeroed on timeout, on navigating `menu_cursor` away from `MAIN_MENU_RESET_INDEX`, and on leaving the menu via `quit_to_menu`, so it can never persist stale across screens. Three module lists cover the three lifecycle steps and are deliberately *not* interchangeable: `LOADABLE_MODULES` (everything with a `.load()`, iterated by `love.load`), `PAUSABLE_MODULES` (what `love.pause()`/`love.resume()` both iterate — not every module, since Background/FXManager keep animating while paused and Bloom/HitEffect/UI/HighScore have no such state), and `RESETTABLE_MODULES` (what `restart_game` wipes — excludes UI/Bloom for having no run state, HighScore because persisting is its entire job, and GameState because the caller sets the target state itself; *includes* Background/FXManager, which the pause list skips). Alongside them, three small helpers keep the file's repeated shapes from drifting apart: `hazard_collision_handler(module, shake_duration, shake_magnitude)`, a factory building the five `love.on_*_player_collision` handlers (Enemy/ZigzagEnemy/Projectile share the regular hazard shake, Mine/Boss the heavier one, and Boss passes `nil` for the module since it has nothing to remove) — they were five hand-copied bodies of the same remove → `is_dead`/`GAME_OVER` guard → `apply_player_hit` sequence, which is exactly how the void-orb-miss handler once silently lost its flicker and death guard; and `step_cursor(cursor, delta, count)`, the single wraparound-arithmetic helper behind `move_main_menu_cursor`/`move_pause_menu_cursor`/`move_card_cursor`, which had been spelled out inline at all six keyboard/gamepad navigation sites.
- `src/screen.lua` — the virtual-resolution layer, and the reason the window can be any size without a single gameplay constant changing. `Screen.WIDTH`/`Screen.HEIGHT` (960x540, 16:9) are **the** play-area dimensions; `Screen.scale`/`offset_x`/`offset_y` are the window→game transform, recomputed in `Screen.load()` and `Screen.update_scale()` (called from `love.resize`, which is all that resizing needs to touch). `Screen.push()`/`pop()` wrap the part of `love.draw` that targets the real window; `Screen.to_game(x, y)` converts `love.mousepressed`'s window coordinates into game coordinates — without it every menu/card click would be off by the letterbox offset and wrong by the scale factor. `Screen.toggle_fullscreen()` backs F11. **The rule that keeps this honest: game logic asks `Screen`, never `love.graphics.getWidth/getHeight`** — this file holds the only remaining call to those, and note it's asking a genuinely different question there ("how big is the window?") than the 80 call sites it replaced were ("how big is the play area?"). Those two used to be the same number, which is exactly what made them so easy to conflate. Scale is uniform (`math.min` of the two axis ratios) rather than per-axis, so the game never stretches; the leftover space stays black, reading as a frame rather than as play area. **The transform is applied before the scene is drawn, not to a finished small image** — see `love.draw` below. `Screen.window_size()` is the deliberate second question ("how many real pixels?"), needed only by the two things that genuinely rasterize per-pixel: Bloom's scene canvases and font sizes. **Fonts are the one thing the transform can't fix on its own** — a glyph is rasterized once at a fixed pixel size, so a 24pt font drawn under a 2.4x transform is a 24px bitmap stretched, exactly the blur native rendering removes everywhere else. `Screen.new_font(game_size)` builds fonts at the pixel size they'll actually occupy, and `Screen.print`/`printf`/`text_width`/`text_height` counter-scale by `1/scale` so every call site still positions and measures text in game units and no layout code knows any of this happened. `UI.refresh_fonts()`/`Debug.refresh_font()` rebuild them from `love.resize`, each guarded on the scale actually having changed so dragging a window edge doesn't rebuild a font on every one of the many events that generates.
- `src/collision.lua` — the two overlap shapes every entity in the game resolves to: `circle_overlaps_player(player, x, y, radius)` (orbs, projectiles, a mine's blast radius) and `rect_overlaps_player(player, x, y, w, h, padding)` (falling hazards, boss bodies — `padding` shrinks the rect **horizontally only**, which is what the hand-written versions all did). Plus `hazard_circle_hits_player`/`hazard_rect_hits_player`, identical except they return false while `player.is_dashing` — so routing every hazard check through them means a new hazard type **can't silently forget dash phase-through**, which is the invariant that actually matters here. Pickups (Orb/VoidOrb) deliberately call the plain overlap tests instead, since dashing into a reward should still collect it. Takes a duck-typed `player`-shaped table and calls `player.center()`. Another read-only "service" module in the `Cards`/`Debug`/`FXManager` mold: `require`d directly as a top-level local, no lifecycle wiring, and it has no requires of its own. Boss's laser keeps its own check (`check_laser_collision`) rather than using either shape — the beam spans the full screen on one axis, so it's a 1-D band test, not a rect.
- `src/game_state.lua` — explicit state machine: `GameState.MENU/PLAYING/PAUSED/CARD_SELECT/GAME_OVER`, `.set()`/`.is()`. Single source of truth for game state — don't reintroduce parallel booleans or per-module mirrors of the same flag.
- `src/pool.lua` — generic object pool (`Pool.new(factory)`, `:spawn(init)`, `:release(index)`, `:clear()`). O(1) swap-and-pop removal, **safe specifically because callers iterate backward** (`for i = #active, 1, -1`) and only ever release at the *current* loop index. Re-verify that invariant before reusing this pattern for a differently-iterated entity type.
- `src/player.lua`, `src/enemy.lua`, `src/zigzag_enemy.lua`, `src/mine.lua`, `src/orb.lua`, `src/void_orb.lua`, `src/projectile.lua` — entity modules. `src/mine.lua` breaks from the rest of the pattern in one respect: its collision check only ever fires once, in a single frame (the instant `arm_timer >= TELEGRAPH_DURATION`), rather than every frame like a contact hazard — no `hit_cooldown` needed, since there's no lingering-overlap case to guard against. It removes itself directly (`Mine.remove(i)`) when the player was clear of the blast, but — matching every other hazard's convention — leaves removal to the caller (`Xxx.remove(index)` inside the `on_collision` handler in `main.lua`) when it did hit, so the object isn't double-released. `Player.take_damage` returns one of `"damaged"/"dead"/"shielded"/"dodged"/"revived"` and callers (`main.lua`) branch on all five; the dash i-frame check and Debug god-mode both also short-circuit straight to `"dodged"`, before shield/dodge-chance/extra-life are even consulted, so dashing/god-mode never burns those resources. Dash invincibility is enforced at **two layers**: `player.is_dashing` gates collision detection itself in every hazard module (true phase-through, no FX/removal), and `take_damage`'s own check is a defensive fallback in case something ever calls it anyway. `Projectile.spawn(x, y, dir_x, dir_y, homing)` — the optional `homing` flag makes a projectile steer its direction toward the player each frame at a clamped turn rate (`steer_towards` local fn, itself built on a hand-written `atan2` from single-arg `math.atan` — `math.atan2` runs fine on LÖVE's LuaJIT but is removed in standard Lua 5.3+ and it's unclear whether the two-arg `math.atan(y,x)` form is safe to assume, so this sidesteps the question entirely) instead of flying straight, and gives it a finite `homing_lifetime` (6s) so it can't chase forever. **Running out of lifetime now detonates it** in a `HOMING_BLAST_RADIUS` (52px) blast that follows the exact shape of `Mine`'s: the explosion and FX happen either way, only a player still inside it (and not dashing) takes the hit, and the caller removes the projectile in that case so it isn't released twice. A green warning ring over the final `HOMING_BLAST_WARNING` (1.0s) telegraphs it, reusing the visual language Mine already taught. `Projectile.clear_homing()` deliberately does **not** detonate — see below. Non-homing projectiles still just rely on leaving the screen bounds to get cleaned up. `Projectile.clear_homing()` clears every active homing shot at once (used when the homing boss leaves — see `boss.lua`'s `on_type_exit`); it spawns the burst FX but deliberately **skips the damaging blast**, since the encounter is already over and killing the player with the debris of a boss that has left is precisely the "threat outliving the boss" problem the function exists to solve. Homing projectiles render green regardless of who fired them. `Player.center()` returns the player's center point as two values and is the single source for it — nearly every collision test and FX spawn wants the center rather than the top-left corner, and it was hand-written at a dozen call sites (including inside `src/collision.lua`, which calls it duck-typed off whatever `player` it's handed). `Player.min_x/min_y/max_x/max_y` are the rect `Player.bounds()` clamps into, replacing the hardcoded screen edges entirely (`Player.reset_bounds()` restores the full screen, called from both `load` and `reset`). `main.lua` is the only writer — it assigns all four from `Boss.get_player_bounds()` every frame — so Player itself doesn't know or care *why* a wall exists. `Player.draw_walls()` draws a faint dashed line along each edge that's actually been pushed in from the screen edge, so a restriction is always visible rather than an invisible wall the player discovers by bumping into it. This started as a single `Player.min_y` scalar for the anti-top-camping wall and was generalized to all four edges for the Warden boss. `Mine.spawn_at(x, y)` drops a mine that's already anchored and arming at an exact spot (clamped on-screen), skipping the falling phase — used by the Bomber boss, which places its bombs deliberately rather than letting them rain from the top; everything after that point (telegraph, blast, damage) is the normal mine path.
- `src/boss.lua` — extension points worth knowing before adding a type: **`movement`** (a function `(instance, type_def, dt, player)` owning where the boss is each hover frame — **all five modes declare that full signature even where they ignore the tail arguments** (`_dt`/`_player`), since they're stored in and called through the one `type_def.movement` slot interchangeably; declaring narrower ones was a lie about the contract and made the Lua Language Server flag the call site with `redundant-parameter` — defaults to the shared sine `patrol_movement`; `orbit_movement`/`bounce_movement`/`charge_movement`/`blink_movement` are the others. This replaced an `if is_orbiter / elseif is_bouncer / else` chain that stopped scaling at four modes; the flags themselves survive because *spawn placement*, the edge clamp and clone-vs-clone collision key off them, which isn't movement); **`fire`** (optional — Charger has none, since its body is the attack — receiving `(instance, type_def, spawn_projectile, player, spawn_mine)`); **`draw_extra(instance, type_def)`** (per-type overlay, each type deciding for itself whether its current phase warrants drawing anything — the laser beam and charger's warning column both go through it); **`player_min_y`** and the warden's `arena_*` instance fields (both feeding `Boss.get_player_bounds`); and two generic per-instance flags, **`alpha`** (draw opacity, phantom-only) and **`intangible`** (switches off collision *and* firing in one go — used by the phantom mid-blink, where either half alone would read as a bug). **Multi-instance**, not a true singleton: `Boss.instances` is a small array (almost always length 1, briefly 2 after a Splitter split), iterated backward like the pool convention (`for i = #active, 1, -1`, remove-at-current-index only) so mid-loop splits/removals are safe. `Boss.active` is a plain boolean kept in sync (true on spawn, false the instant the instance list empties) — every other module still just reads it as before. Per-type behavior lives in a `BOSS_TYPES` registry (`id -> {width, height, colors, patrol_amplitude/speed OR is_orbiter+orbit_radius/orbit_center_y/speed, fire fn, optional fire_second fn, optional player_min_y}`); shared code (enter/exit movement, the sine-patrol horizontal movement — `patrol_amplitude = 0` gives "stationary" for free — AABB collision, rounded-rect draw) lives once in the module and reads whichever type's config applies. `patrol_amplitude` for every sine-patrol type must be large enough to actually reach both screen edges from its spawn `base_x` (a centered `base_x` needs `amplitude >= half the screen minus half the boss width`) — Sentinel/Splitter both originally fell well short of this, leaving a permanently-unvisited strip on both sides of the screen no matter what else patched the top-camping exploit; values were corrected once this was noticed. `splitter_clone` doesn't use the sine patrol at all (`is_bouncer = true`): it moves in a straight line at a constant `bounce_speed`, reversing `bounce_dir` off the screen edges (in the same clamp block that would otherwise just stop a sine-patrol type) and off the other clone via the module-level `resolve_bouncer_collisions(instances)` helper (called once per frame from `Boss.update`, after both instances have moved) — sine-patrolling clones off a shared formula with only a small spawn-offset between them made them drift side-by-side in near lockstep, and giving that sine enough amplitude to reach either edge from an arbitrary split position also made them absurdly fast (amplitude directly scales peak velocity). The collision check pushes both clones' directions explicitly *away* from each other (not a toggle) whenever their bounding boxes overlap, so re-triggering every frame while still overlapping can't cause flip-flip jitter — it just keeps asserting "apart" until they've actually separated. `fire_aimed_shot` is a single shot computed once toward the player's *current* position at fire time (not steering afterward, unlike homing) — closes any geometric gap a fixed angle/fan can't (corners included). Laser still uses it for its independent aimed shot. Sentinel/Splitter/splitter_clone used it too for a time (a `guard_interval`/`guard_fire` hook, added specifically to fight top-camping) but that was removed once `Player.min_y` made it redundant — denying the position outright beats out-tracking a player already standing in it. All hazard collision checks (`check_instance_collision`, `check_laser_collision`) skip entirely while `player.is_dashing`. A generic `instance.pending_second_burst` countdown (ticked in `update_instance` right after the normal fire step, harmless/no-op for any type that doesn't set it) calls `type_def.fire_second` once it elapses. **It clears the field *before* calling `fire_second`, which means `fire_second` can re-arm it and chain** — that's what lets Turret run 2-3 rings and Phantom 2-3 alternating bursts off one volley without any new mechanism. Four types use it now: Turret (cycling ring counts), Phantom (alternating +/X bursts), Sentinel (35% chance of a rotated double), Splitter's clones (22% chance), and Bomber (its projectile volley, offset 0.5s from its bombs). `fire_spread` accepts `rotation_offset` for **fans as well as rings**, which is what lets a follow-up volley thread the gaps of the one before it rather than being a plain repeat. `is_orbiter` (Turret) branches to circular motion around a fixed arena point instead of the sine patrol — **`Boss.spawn` and the enter-phase target Y both special-case orbiters to land exactly at the orbit formula's angle-0 position**, otherwise hover starts with an instant jump from the generic entry point to wherever the orbit math first evaluates to (this bit us once already — same class of bug as the original patrol "zip," same fix: make the starting reference match). Laser's beam is its own self-contained sub-system (`laser_state`: cooldown → telegraph → firing) drawn as a **full-width or full-height band that sweeps edge-to-edge across the entire screen** (`laser_axis` picks horizontal/vertical, `laser_row_start`/`laser_row_end` are the two screen edges in the direction chosen, interpolated into `laser_row_y` during firing) — earlier versions used a fixed pivot, then a small-range slide, and both still left some region of the arena permanently safe; a full edge-to-edge sweep across a randomized axis/direction doesn't. Laser's aimed projectile shot (via the shared `fire_aimed_shot` helper) runs on its own independent timer (`shot_timer`/`LASER_SHOT_INTERVAL`), decoupled from the beam's cooldown/telegraph/firing cycle so it can fire more often than the beam cycles. Laser's exit condition is **shot-count-based, not time-based**: `instance.laser_sweep_count` increments each time a firing phase completes, and the type branches to check that against `LASER_MAX_SWEEPS` instead of the shared `hover_timer >= ENCOUNTER_DURATION` every other type uses — the two budgets didn't line up, so the boss could previously exit mid-telegraph or truncate the last sweep. `Boss.update`/`update_instance` take an optional `on_type_exit(type_id)` callback, fired once exactly when an instance's phase flips to `"exit"` — `main.lua` uses it to call `Projectile.clear_homing()` specifically when the leaving type is `"homing"`, but the hook itself is generic (any type could react to its own exit this way, not just Homing). `Boss.debug_summary()` returns a one-line `"type:phase/detail, type:phase/detail"` string for the debug overlay, where `detail` comes from an optional per-type **`debug_state(instance)`** — the generic `phase` sits at `"hover"` for an entire encounter, so it hides the sub-state machine most types actually run on (set for `laser` (beam state + sweep count, since sweeps are its real exit condition), `charger`, `phantom` (including whether it's currently `intangible`) and `warden` (its live arena size, hover-only and rounded, since a stale exit-phase value would describe a wall that's no longer enforced)). `Boss.get_player_bounds()` returns the rect the player is confined to this frame as `min_x, min_y, max_x, max_y` — the full screen unless a live encounter narrows it. Two kinds of restriction feed in: the opt-in per-type `type_def.player_min_y` (set on `sentinel`/`homing`/`splitter`/`splitter_clone`/`charger`/`bomber`, walling off the top of the screen so they can't be camped above) and the warden's per-instance `arena_min_x`/`arena_max_x`/`arena_min_y` (written each frame by `update_warden_arena`, shrinking all the way in over its encounter). It only counts instances in `"hover"` — during enter/exit the boss isn't threatening that space yet/anymore — and combines multiple instances to the **tightest of each edge** rather than first-wins. `main.lua` writes all four straight into `Player` every frame, so restrictions turn on/off automatically as encounters start and end, and Player itself never knows why.
- `src/fx_manager.lua` — particle-system templates + expanding "ring" shockwave effect (`spawn_ring`). `FXManager.spawn(name, ...)` silently no-ops on an unknown template name.
- `src/background.lua` — parallax starfield. Paints its backdrop with a filled rect over the play area rather than `love.graphics.clear`: clear ignores the current transform and would flood the whole canvas, which is now the whole window, filling the letterbox bars with the backdrop color instead of leaving them black.
- `src/ui.lua` — HUD + menu/pause/game-over/card-select overlay text, driven by `GameState.current`. `UI.card_layout()` is the single source of truth for the 3 card rectangles, shared with `main.lua`'s mouse-click hit-testing so visuals and click boxes can't drift — the card-select appear animation (below) is purely a *draw-time* transform layered on top of those same rects via `love.graphics.push/translate/scale/pop`, so it can never desync from the click boxes. `UI.draw_card_select(cards, cursor_index, elapsed, chosen_index)` eases each card in (85%→100% scale, small rise, fade-in) over `CARD_ANIM_DURATION`, staggered `CARD_STAGGER` seconds apart per card index for a left-to-right cascade; when `chosen_index` is set (during `main.lua`'s post-pick confirm delay) the chosen card gets a gold highlight and the other two dim to 35% alpha instead of animating further. The "BOSS INCOMING"/"HAZARD STORM"/"STORM INCOMING" banners (`UI.draw`, priority order boss_active > boss_incoming > storm_active > storm_incoming — all four are mutually exclusive in time by construction in `main.lua`) each pulse via a plain `love.timer.getTime()` sine, no extra per-banner state needed; the active-storm banner flickers noticeably faster (12 vs 6) than the two telegraph banners, since it means "danger right now" rather than "danger soon." `UI.simple_menu_layout(count, top_y)`/`UI.draw_simple_menu(labels, cursor_index, top_y)` are a small shared vertical button-list widget used by both the main menu and pause — same single-source-of-truth pattern as `card_layout()` (`UI.main_menu_layout()`/`UI.pause_menu_layout()` wrap it with each screen's own fixed `top_y`, called by `main.lua` for mouse hit-testing too). Deliberately simpler than the card-select treatment (no appear animation, no stagger) since picking a card is the core roguelike decision and these are just navigation. `UI.draw_simple_menu` takes an optional `danger_index` — the one button it renders in a red warning color/border regardless of hover state, used by the main menu's armed "Reset High Score" (relabeled to "Click again to confirm" while armed, both computed in `UI.draw_menu` from a `reset_armed` flag `main.lua` passes in).
- `src/difficulty.lua` — wave counter + spawn-rate lerp. `Difficulty.wave()` and `Difficulty.skip_wave()` both go through a shared local `wave_at(elapsed)` helper (returns the wave number plus that wave's `[start, end)` boundary) so the two can't drift out of sync — `wave()` just reads the number, `skip_wave()` (the debug hotkey) jumps `elapsed` precisely to the next wave's boundary regardless of how far into the current wave it was. `EARLY_WAVE_DURATIONS` gives waves 1-3 a shorter length than the steady-state `WAVE_DURATION`; `RAMP_WAVES` (used only in `spawn_rate`) is a fixed real-time budget (`RAMP_WAVES * WAVE_DURATION` seconds) for the density ramp, deliberately decoupled from wave *number* so shortening early waves doesn't also warp how fast spawn rates ramp.
- `src/bloom.lua` — render scene to a canvas, bright-pass threshold + separable gaussian blur, additive composite into `Bloom.final_canvas`. **Two canvas families, sized off deliberately different things.** `scene_canvas`/`final_canvas` match the *window* (rebuilt by `Bloom.resize()` from `love.resize`), so the scene rasterizes at native resolution and `HitEffect.draw` blits the result 1:1 with no resampling. The blur canvases (`bright`/`ping`/`pong`) stay fixed at half the *game's* resolution no matter how big the window is: the blur kernel is a fixed 4 texels wide, so its reach in game units is set entirely by that size, and following the window would quietly tighten the glow as the window grew — changing the look the whole palette was tuned against. Blurred output is low-frequency by definition, so computing it small and upscaling on composite is free visually and cheaper besides. **The threshold shader uses max-channel brightness, not perceptual luminance** — perceptual weights (favoring green) unfairly discount saturated reds/blues/purples, so a fully-lit red or purple shape would never bloom under the "correct-looking" luma formula. Keep this in mind when picking colors for new entities (e.g. future boss variants) if you want them to glow.
- `src/hit_effect.lua` — post-processes `Bloom.final_canvas` before it hits the screen: `hit_strength` (decaying, triggered on damage) drives chromatic aberration + vignette; `danger_strength` (continuous, driven by `Player.lives == 1`) drives an independent red-tint pulse. Two separate uniforms so the two effects can stack without fighting.
- `src/high_score.lua` — `love.filesystem` read/write, simple "only overwrite if higher" save. `HighScore.reset()` writes `0` straight to the save file and `HighScore.value`, no confirmation logic in this module — that lives entirely in `main.lua`/`src/ui.lua` (see the reset-confirm-arm note below), keeping this module a plain dumb read/write/reset API.
- `src/cards.lua` — the roguelike layer. `CARD_POOL` (20 defs: `id/name/description/max_stacks/on_pick/modifiers`), `Cards.owned` (stack counts), `Cards.modifiers` (flat table, **fully recomputed from `owned` on every pick** — declarative, not incrementally mutated). `Cards.get(key, default)` is the read API every other module uses. Two cards (Guardian Aura, Regeneration) tick continuously via `Cards.update` and "bank" their trigger — if the condition (shieldless / missing HP) isn't met when the timer completes, it holds at cap and fires the instant the condition becomes true, rather than needing exact timing.
- `src/debug.lua` — F1-toggle overlay + hotkeys; reads `Cards.modifiers`/`Cards.owned` directly for the readout. Owns the boss-spawn cycling state (`Debug.next_boss_index`, `Debug.cycle_boss(sequence)` for F3 and `Debug.select_boss(index, sequence)` for the 1-9 keys — both take the roster as a parameter rather than requiring `Boss`, and `select_boss` returns nil for any non-index so `main.lua` can fall through to whatever else that key does). Deliberately *not* reset by `restart_game`: it's testing state, not run state. `Debug.draw` also takes `unlock_stage`/`max_unlock_stage` from `main.lua` (shown as "Unlock stage: X/3" on the state line) purely for visibility while testing the progressive hazard-unlock system — everything else it reads it pulls straight from the modules it already required.

No assets/sprites/audio — everything is drawn procedurally. User explicitly doesn't want music.

46. **Native-resolution rendering** (immediate follow-up to 45 — the user reported the scaled window looked blurry, which it did). Item 45 rendered the scene into an 800x600 canvas and stretched that raster up, which is the right pattern for a *sprite* game and the wrong one here: this game has no assets at all, every entity is `love.graphics.rectangle/circle/polygon/line`, and vector geometry has no native resolution to preserve — drawing it under a scale transform costs exactly the same and stays sharp. So the transform moved to *before* the scene is drawn instead of after: `Screen.push()` now wraps the scene render inside `love.draw`, Bloom's `scene_canvas`/`final_canvas` follow the window (rebuilt by a new `Bloom.resize()`), and `HitEffect.draw` blits 1:1. Three things needed care rather than a straight swap. (a) Bloom's *blur* canvases deliberately do **not** follow the window — the kernel is a fixed 4 texels, so window-sized blur canvases would have tightened the glow as the window grew; they stay pinned to half the game resolution, which keeps the tuned look and is cheaper. (b) `Background.draw` used `love.graphics.clear`, which ignores the transform and would have flooded the letterbox bars with the backdrop color now that the canvas is the whole window — replaced with a filled rect over the play area. (c) Fonts can't be fixed by a transform at all, since a glyph is rasterized once at a fixed pixel size; `Screen.new_font` builds them at their real on-screen size and `Screen.print`/`printf`/`text_width`/`text_height` counter-scale by `1/scale`, so all ~37 call sites in `ui.lua`/`debug.lua` still work in game units. Verified by actually looking at it this time: captured screenshots at 1200x900 and at a deliberately 16:9 1600x900 (confirming black bars, not backdrop-colored ones), plus a late-Warden-encounter frame confirming the dashed arena walls still render after the dimension swap.

    - The mechanical part (the letterbox transform in `src/screen.lua`) needed zero changes — `Screen.update_scale()` already used `math.min` of both axis ratios generically, never assumed 4:3.
