# Neon Dodge — Project Notes

A LÖVE2D (Lua) project the user is building specifically **to learn LÖVE and Lua**. Not a shipping product — every feature is chosen for what it teaches, so lean toward explaining/using idiomatic LÖVE patterns over the fastest hack. This file exists because the coding session this project was being developed in was rooted in an unrelated repo (`kensan_app`, a Flutter project) and couldn't be switched — start fresh sessions with this file's directory (`NeonDodge/`) as the actual working directory/root so tools resolve paths correctly.

**Claude Code sessions do not sync across the user's machines** (confirmed — session history is local/per-install, not account-synced even in the desktop app). This file is the actual continuity mechanism between machines/sessions: keep it current. See the last working agreement below.

## What the game is

Top-down dodge/collect arcade game, 800x600 window, no resize.
- Player: cyan square. Move with WASD/arrows or a gamepad's left stick/d-pad. Shift or gamepad A dashes (0.1s burst, 0.75s cooldown, both tunable by cards) — **the player is a true phase-through while dashing**, not just damage-immune: every hazard's collision check (Enemy, ZigzagEnemy, Boss body, Boss laser, Projectile) skips entirely while `player.is_dashing`, so nothing gets destroyed/consumed and no FX/hitstop fires either, on top of `take_damage` itself short-circuiting to `"dodged"` as a defensive fallback. Orb/VoidOrb pickups are deliberately *not* phased — they're beneficial, so dashing through them still collects them. This is what makes the Quick Dash/Long Dash cards genuinely defensive tools, not just mobility.
- HP: 3 max by default, shown as hearts top-left. Max HP can change at runtime via cards (Vitality +1, Glass Cannon -1).
- Red triangles ("Enemy") fall from top → touching one costs 1 HP. Speed ramps +5 per miss, capped (`Enemy.max_speed`) so it can't run away unbounded.
- Orange/red-ish diamond ("ZigzagEnemy") — same damage rule and capped ramp as Enemy, but sine-waves horizontally while falling. Fill `(1, 0.4, 0.05)` with a dark red `(0.7, 0, 0)` outline for readability against the yellow orb.
- Yellow circles ("Orb") → +5 score. Every 5th orb: heals +1 HP if not at max HP, otherwise **grants a one-hit shield instead** (only if not already shielded). The "Orbs: X/5" HUD counter shows progress toward that next milestone (wraps every 5, showing 5/5 right at the trigger moment), not the lifetime total.
- Purple orbs ("VoidOrb") → +10 score on catch; **missing** one costs 1 HP (unless the Void Ward card is active); its fall speed is eased by the same "Slow Fall" card modifier as Enemy/ZigzagEnemy, since missing one has a real HP cost like touching a hazard does (Orb, a pure pickup with no downside, is deliberately not affected).
- Bronze/copper octagon ("Mine") — a genuinely different kind of hazard: the body itself is harmless, only its shockwave deals damage. Falls slowly, anchors in place at a random height, then arms: a growing warning ring appears at its blast radius immediately (so there's maximal time to route around it), and its core flashes hotter orange-red and faster as the ~1.3s telegraph runs out. On detonation, only a player still inside the blast radius (dash phase-through still applies) takes 1 HP, boss-tier shake (0.2/8, bigger than a normal hazard touch); the mine is removed either way. "Dodge the moving shape" vs. "be clear of this zone by the deadline" — the first hazard in the game that isn't a contact-on-touch threat.
- Shield: one-hit block, blue ring wrapping the player, quick pop-in animation then holds fixed size/alpha (no continuous pulsing).
- Boss: spawns every 6th wave (`BOSS_WAVE_INTERVAL` in `main.lua`), ~14s encounter then leaves on its own (game is pure-dodge, no player attack, so every boss is a survive-the-encounter set piece, not a fight). Touching a boss body costs 1 HP, gated by a hit-cooldown so overlap doesn't melt HP every frame. Surviving it awards bonus score and opens the card-select screen. Three deliberate breathers pace these transitions instead of snapping straight through them: a **"BOSS INCOMING" telegraph** (`BOSS_INCOMING_DELAY`, 1.6s — existing hazards keep falling but no new ones spawn, and a pulsing warning shows) before the boss actually appears; a **freeze-frame beat** (`POST_BOSS_PAUSE_DURATION`, 1.0s — the whole game visibly holds still) after the boss dies and before the card screen opens; and a **confirm hold** (`CARD_CONFIRM_DELAY`, 0.4s — the picked card stays highlighted, the other two dim) after choosing a card and before play actually resumes. **Five distinct boss types cycle in a fixed escalating sequence** (`BOSS_SEQUENCE` in `main.lua`: sentinel → homing → laser → splitter → turret → repeats):
  - **Sentinel** patrols horizontally (full screen width, see below) + fires a 7-shot downward spread. Multiple attempts were made to stop players camping above it: a fixed upward fan (blocked by corners), then a shot tracking the player's real position (still trivially dodgeable as a single periodic projectile from a static spot) — both were dropped in favor of denying the position outright: it's bigger-bodied (90x60 → 125x75) and walls off the top of the screen entirely for the duration of the encounter (`Player.min_y`, drawn as a faint dashed line) so "stand above the boss" isn't a legal position at all.
  - **Homing** patrols slower and fires rare projectiles that curve toward the player (steering/vector-math exercise); homing shots expire after 6s (with a small green burst FX) so they can't chase forever once the encounter's over. Any still-active homing shots are also explosion-cleared the instant the boss itself starts leaving, so its threat doesn't outlive it even within that 6s window. Also enforces the same `Player.min_y` top-of-screen wall as Sentinel/Splitter — its own shots steer continuously so coverage was never the issue, but a player parked far enough above still had time to read and juke each shot before it curved into range.
  - **Laser** barely moves but its beam does: a full-width **or** full-height band that sweeps edge-to-edge across the *entire* screen, randomly one of left→right / right→left / top→bottom / bottom→top each cycle (cooldown → telegraph → firing). Telegraph shows a single line at the start position only (an end-line too was tried and dropped — with a full edge-to-edge sweep the far end is always a screen edge, so showing it added confusion, not clarity). The encounter tracks completed sweeps directly (`laser_sweep_count`) and exits only once exactly 4 have finished, instead of sharing the generic per-type time budget — that budget didn't line up with the beam's own cycle length, so the boss could leave mid-telegraph or cut the last sweep off partway through. Also fires a straight (non-homing) aimed shot at the player on its own independent ~1s cadence, decoupled from the beam cycle so shots don't wait on it — this is the one place `fire_aimed_shot` is still used; Sentinel/Splitter's own aimed "guard" shots were removed once the `Player.min_y` wall made them redundant.
  - **Splitter** is small/fast and splits into two smaller independent clones partway through its encounter (8-shot spread original, clones a bit weaker at 6) — the original (65x45 → 85x55) also enforces the same top-of-screen `Player.min_y` wall as Sentinel for its whole encounter (clones keep their smaller size but still enforce the wall, at a slightly lower line matching their shorter body). The original patrols the *full* screen width now — its `patrol_amplitude` used to fall well short of actually reaching the screen edges from its spawn point, leaving a permanently-unvisited strip on both sides. The clones don't sine-patrol at all: they ping-pong in a straight line at a fixed speed, reversing off the screen edges *and* off each other (`is_bouncer`/`bounce_dir`/`bounce_speed`, resolved each frame by `resolve_bouncer_collisions`) — sine-patrolling both off a shared formula made them drift side-by-side in near lockstep instead of splitting up to cover the arena, and giving that sine a wide-enough amplitude to reach both edges from any split position also made them absurdly fast.
  - **Turret** orbits in a circle around a fixed arena point (not stationary) and fires full-circle projectile rings that rotate their angle offset a little more each burst (a slow bullet-hell spiral) — each volley is actually **two** rings back to back, ~0.18s apart, the second interleaved exactly into the first's gaps (offset by half the ring's angular spacing), so dodging one ring's pattern isn't enough.
- Debug's **F3** hotkey cycles through all 5 boss types independently of the real in-run sequence, for fast testing.
- **Roguelike card system**: after every boss encounter, gameplay pauses and offers 3 of 20 cards (see `src/cards.lua`) — pick via mouse click, number keys 1/2/3, WASD/arrows + Enter/Space, or gamepad d-pad + A. Effects span survivability (+max HP, auto-shield/regen ticking, dodge chance, banked extra-life revives, Void Ward), score (flat bonuses, multipliers, low-HP double-score), mobility (move speed, dash cooldown/duration), and hazard-easing (fall speed, enemy speed-ramp, hitstop/shake intensity).
- Wave-based difficulty: spawn rates ramp over ~2 minutes via `src/difficulty.lua`; `Difficulty.wave()` drives both the boss cadence and the UI wave counter. Waves 1-3 are shorter than the steady-state 20s (10s/13s/16s) so the early game escalates noticeably faster instead of an uneventful sit before anything changes — wave 4 onward is a flat 20s.
- **Hazard storms**: every 3rd wave that *isn't* a boss wave (with `BOSS_WAVE_INTERVAL` a multiple of `STORM_WAVE_INTERVAL`, storms and bosses naturally alternate every 3 waves with no gaps), a ~1.2s "STORM INCOMING" warning plays (gameplay unchanged — the point is "brace yourself", unlike the boss telegraph's "things calm down"), then a 10s "HAZARD STORM" where Enemy and Orb both spawn roughly 3x more often — a red-triangle swarm with more yellow-orb pickups as the reward for braving it — before dropping back to normal. ZigzagEnemy, Mine, and VoidOrb are suppressed entirely for the storm's duration rather than also sped up: stacking every hazard type's density at once turned it into an unsurvivable pile-up in practice, so storms deliberately narrow down to one hazard type instead of piling all of them on.
- **Progressive hazard unlocks**: instead of every hazard/pickup type being live from wave 1 with only their spawn *rate* ramping, the roster itself grows one event at a time. Only Enemy and Orb are ever active from the start; the first boss or storm to conclude unlocks VoidOrb, the second unlocks ZigzagEnemy, the third (and every one after) unlocks Mine. With the current 6/3 boss/storm cadence this lands as: waves 1-3 Enemy+Orb only, VoidOrb after the wave-3 storm, ZigzagEnemy after the wave-6 boss, Mine (full roster) after the wave-9 storm. Each new type's introduction rides on an event milestone that already exists, rather than adding a separate unlock timer.
- Screen-space shaders, always layered: bloom/glow (`src/bloom.lua`) on the whole scene, plus an on-hit chromatic-aberration + vignette pulse and an automatic red "heartbeat" vignette while at 1 HP (`src/hit_effect.lua`).
- Persistent high score via `love.filesystem` (`src/high_score.lua`), shown on the menu and game-over screens.
- Debug mode (**F1** to toggle) — bottom-screen overlay of state/wave/boss/player HP/active card modifiers/owned cards. While enabled: **F2** forces a card-select screen, **F3** force-spawns the boss, **F4** skips a full wave forward, **F5** toggles god mode (no damage).
- Game states: `menu` → `playing` → `paused` (P / gamepad Start) → `card_select` (after every boss) → `game_over` (R / gamepad A to restart).

## Architecture

Module-per-entity pattern in `src/`, each module is a table returned from its file, generally exposing `load/update/draw/pause/resume/reset`. Modules receive sibling modules as parameters where practical (e.g. `Enemy.update(dt, game_over, player, on_collision, spawn_rate)`); a few modules (`Cards`, `Debug`, `FXManager`) are `require`d directly by others since they're read-only "service" lookups rather than entities needing lifecycle wiring — this is an established, intentional exception, not drift to fix.

- `main.lua` — owns score, orb count, screen-shake state, hit-stop timer, wave/boss/card trigger bookkeeping; wires modules together via callback functions passed into each module's `update`. Centralizes card-modifier application for anything that isn't naturally owned by one module (`love.shake`/`love.hitstop` multiply by `shake_mult`/`hitstop_mult`; `love.increase_score` applies `score_mult`/`low_hp_score_mult` and rounds to an integer — a fractional multiplier like Glass Cannon's 1.5x will otherwise leave float scores). Three transition timers pace the normal→boss→card-select→normal flow, all ticked in `love.update`: `boss_incoming_timer` (defers the actual `Boss.spawn` call, suppressing new hazard spawns via `suppress_spawns` in the meantime — existing hazards keep falling, only new spawns stop), `post_boss_pause_timer` (set by `on_boss_encounter_end` instead of calling `trigger_card_select` immediately; ticked with an early `return` right after the `hitstop_timer` check, the same "skip the rest of this frame" trick hitstop already uses, so the whole game visibly freezes for the duration), and `card_confirm_timer` (set by `choose_card` instead of resuming immediately, ticked inside the `CARD_SELECT` branch of `love.update`, calling `finish_card_select()` once it elapses). `trigger_card_select`/`finish_card_select` are **forward-declared** (`local trigger_card_select` etc. near the top of the file, assigned later without the `local` keyword) specifically so `love.update` — defined earlier in the file — can call them; Lua resolves `local` scope by textual position, not call order, so without the forward declaration `love.update` would see them as undefined globals. `trigger_card_select` defensively clears `post_boss_pause_timer`/`pending_card_select` on entry so it can't misbehave if reached a different way (e.g. debug F2) than the delayed path. Storm events (`storm_telegraph_timer`, `storm_timer`) are scheduled the same wave-transition way boss encounters are (`wave > last_storm_wave and wave % STORM_WAVE_INTERVAL == 0`), with an explicit `wave % BOSS_WAVE_INTERVAL ~= 0` guard so a storm can never land on a boss wave — the two systems are otherwise completely independent. `storm_rate_mult` (1 normally, `STORM_SPAWN_RATE_MULT` during a storm) speeds up only Enemy and Orb's `Difficulty.spawn_rate(...)` call; ZigzagEnemy/Mine/VoidOrb instead get their spawn rate forced to `math.huge` (same suppression technique as `suppress_spawns` during a boss) for the storm's duration — an early version sped up every hazard type at once, which made storms nearly unsurvivable, so the fix was to narrow the *mix* down to one hazard type rather than just tuning the multiplier. `src/difficulty.lua` itself is untouched either way — the ramp stays the ramp, storms are a `main.lua`-level event layered on top. A single `unlock_stage` counter (0-3, `UNLOCK_STAGE_VOID_ORB`/`_ZIGZAG`/`_MINE` mark the thresholds) gates whether VoidOrb/ZigzagEnemy/Mine are even eligible to spawn at all — each is forced to `math.huge` alongside the existing `suppress_spawns`/`storm_active` checks until `unlock_stage` reaches its threshold. It's incremented by exactly 1 (capped at `MAX_UNLOCK_STAGE`) from two places: `love.on_boss_encounter_end` and the `storm_timer` tick block the instant it crosses back to 0 — i.e. once an event *concludes*, not when it starts, matching "unlock the next thing after that boss/storm" rather than "at the start of it."
- `src/game_state.lua` — explicit state machine: `GameState.MENU/PLAYING/PAUSED/CARD_SELECT/GAME_OVER`, `.set()`/`.is()`. Single source of truth for game state — don't reintroduce parallel booleans or per-module mirrors of the same flag.
- `src/pool.lua` — generic object pool (`Pool.new(factory)`, `:spawn(init)`, `:release(index)`, `:clear()`). O(1) swap-and-pop removal, **safe specifically because callers iterate backward** (`for i = #active, 1, -1`) and only ever release at the *current* loop index. Re-verify that invariant before reusing this pattern for a differently-iterated entity type.
- `src/player.lua`, `src/enemy.lua`, `src/zigzag_enemy.lua`, `src/mine.lua`, `src/orb.lua`, `src/void_orb.lua`, `src/projectile.lua` — entity modules. `src/mine.lua` breaks from the rest of the pattern in one respect: its collision check only ever fires once, in a single frame (the instant `arm_timer >= TELEGRAPH_DURATION`), rather than every frame like a contact hazard — no `hit_cooldown` needed, since there's no lingering-overlap case to guard against. It removes itself directly (`Mine.remove(i)`) when the player was clear of the blast, but — matching every other hazard's convention — leaves removal to the caller (`Xxx.remove(index)` inside the `on_collision` handler in `main.lua`) when it did hit, so the object isn't double-released. `Player.take_damage` returns one of `"damaged"/"dead"/"shielded"/"dodged"/"revived"` and callers (`main.lua`) branch on all five; the dash i-frame check and Debug god-mode both also short-circuit straight to `"dodged"`, before shield/dodge-chance/extra-life are even consulted, so dashing/god-mode never burns those resources. Dash invincibility is enforced at **two layers**: `player.is_dashing` gates collision detection itself in every hazard module (true phase-through, no FX/removal), and `take_damage`'s own check is a defensive fallback in case something ever calls it anyway. `Projectile.spawn(x, y, dir_x, dir_y, homing)` — the optional `homing` flag makes a projectile steer its direction toward the player each frame at a clamped turn rate (`steer_towards` local fn, itself built on a hand-written `atan2` from single-arg `math.atan` — `math.atan2` runs fine on LÖVE's LuaJIT but is removed in standard Lua 5.3+ and it's unclear whether the two-arg `math.atan(y,x)` form is safe to assume, so this sidesteps the question entirely) instead of flying straight, and gives it a finite `homing_lifetime` (6s, small green burst FX on expiry) so it can't chase forever; non-homing projectiles still just rely on leaving the screen bounds to get cleaned up. `Projectile.clear_homing()` explosion-clears every active homing shot at once (used when the homing boss leaves — see `boss.lua`'s `on_type_exit`). Homing projectiles render green regardless of who fired them. `Player.min_y` (default 0) is a second, dynamic lower bound on `Player.y` enforced in `Player.bounds()` alongside the screen edges, and drawn as a faint dashed line across the screen whenever it's raised above 0 — `main.lua` is the only writer (`Player.min_y = Boss.get_player_min_y() or 0`, every frame), so Player itself doesn't know or care *why* the wall exists.
- `src/boss.lua` — **multi-instance**, not a true singleton: `Boss.instances` is a small array (almost always length 1, briefly 2 after a Splitter split), iterated backward like the pool convention (`for i = #active, 1, -1`, remove-at-current-index only) so mid-loop splits/removals are safe. `Boss.active` is a plain boolean kept in sync (true on spawn, false the instant the instance list empties) — every other module still just reads it as before. Per-type behavior lives in a `BOSS_TYPES` registry (`id -> {width, height, colors, patrol_amplitude/speed OR is_orbiter+orbit_radius/orbit_center_y/speed, fire fn, optional fire_second fn, optional player_min_y}`); shared code (enter/exit movement, the sine-patrol horizontal movement — `patrol_amplitude = 0` gives "stationary" for free — AABB collision, rounded-rect draw) lives once in the module and reads whichever type's config applies. `patrol_amplitude` for every sine-patrol type must be large enough to actually reach both screen edges from its spawn `base_x` (a centered `base_x` needs `amplitude >= half the screen minus half the boss width`) — Sentinel/Splitter both originally fell well short of this, leaving a permanently-unvisited strip on both sides of the screen no matter what else patched the top-camping exploit; values were corrected once this was noticed. `splitter_clone` doesn't use the sine patrol at all (`is_bouncer = true`): it moves in a straight line at a constant `bounce_speed`, reversing `bounce_dir` off the screen edges (in the same clamp block that would otherwise just stop a sine-patrol type) and off the other clone via the module-level `resolve_bouncer_collisions(instances)` helper (called once per frame from `Boss.update`, after both instances have moved) — sine-patrolling clones off a shared formula with only a small spawn-offset between them made them drift side-by-side in near lockstep, and giving that sine enough amplitude to reach either edge from an arbitrary split position also made them absurdly fast (amplitude directly scales peak velocity). The collision check pushes both clones' directions explicitly *away* from each other (not a toggle) whenever their bounding boxes overlap, so re-triggering every frame while still overlapping can't cause flip-flip jitter — it just keeps asserting "apart" until they've actually separated. `fire_aimed_shot` is a single shot computed once toward the player's *current* position at fire time (not steering afterward, unlike homing) — closes any geometric gap a fixed angle/fan can't (corners included). Laser still uses it for its independent aimed shot. Sentinel/Splitter/splitter_clone used it too for a time (a `guard_interval`/`guard_fire` hook, added specifically to fight top-camping) but that was removed once `Player.min_y` made it redundant — denying the position outright beats out-tracking a player already standing in it. All hazard collision checks (`check_instance_collision`, `check_laser_collision`) skip entirely while `player.is_dashing`. A generic `instance.pending_second_burst` countdown (ticked in `update_instance` right after the normal fire step, harmless/no-op for any type that doesn't set it) calls `type_def.fire_second` once it elapses — Turret is currently the only type using it, firing a second ring ~0.18s after the first at a half-step rotation offset so the two rings interleave into one denser lattice instead of one being simply a delayed repeat. `is_orbiter` (Turret) branches to circular motion around a fixed arena point instead of the sine patrol — **`Boss.spawn` and the enter-phase target Y both special-case orbiters to land exactly at the orbit formula's angle-0 position**, otherwise hover starts with an instant jump from the generic entry point to wherever the orbit math first evaluates to (this bit us once already — same class of bug as the original patrol "zip," same fix: make the starting reference match). Laser's beam is its own self-contained sub-system (`laser_state`: cooldown → telegraph → firing) drawn as a **full-width or full-height band that sweeps edge-to-edge across the entire screen** (`laser_axis` picks horizontal/vertical, `laser_row_start`/`laser_row_end` are the two screen edges in the direction chosen, interpolated into `laser_row_y` during firing) — earlier versions used a fixed pivot, then a small-range slide, and both still left some region of the arena permanently safe; a full edge-to-edge sweep across a randomized axis/direction doesn't. Laser's aimed projectile shot (via the shared `fire_aimed_shot` helper) runs on its own independent timer (`shot_timer`/`LASER_SHOT_INTERVAL`), decoupled from the beam's cooldown/telegraph/firing cycle so it can fire more often than the beam cycles. Laser's exit condition is **shot-count-based, not time-based**: `instance.laser_sweep_count` increments each time a firing phase completes, and the type branches to check that against `LASER_MAX_SWEEPS` instead of the shared `hover_timer >= ENCOUNTER_DURATION` every other type uses — the two budgets didn't line up, so the boss could previously exit mid-telegraph or truncate the last sweep. `Boss.update`/`update_instance` take an optional `on_type_exit(type_id)` callback, fired once exactly when an instance's phase flips to `"exit"` — `main.lua` uses it to call `Projectile.clear_homing()` specifically when the leaving type is `"homing"`, but the hook itself is generic (any type could react to its own exit this way, not just Homing). `Boss.debug_summary()` returns a one-line `"type:phase, type:phase"` string for the debug overlay. `type_def.player_min_y` (set on `sentinel`/`splitter`/`splitter_clone` only) is an opt-in per-type field read by `Boss.get_player_min_y()`, which scans `Boss.instances` and returns the first one it finds (or nil) — `main.lua` writes that straight into `Player.min_y` every frame, so the restriction turns on/off automatically as those specific encounters start/end and never touches Homing/Laser/Turret.
- `src/fx_manager.lua` — particle-system templates + expanding "ring" shockwave effect (`spawn_ring`). `FXManager.spawn(name, ...)` silently no-ops on an unknown template name.
- `src/background.lua` — parallax starfield.
- `src/ui.lua` — HUD + menu/pause/game-over/card-select overlay text, driven by `GameState.current`. `UI.card_layout()` is the single source of truth for the 3 card rectangles, shared with `main.lua`'s mouse-click hit-testing so visuals and click boxes can't drift — the card-select appear animation (below) is purely a *draw-time* transform layered on top of those same rects via `love.graphics.push/translate/scale/pop`, so it can never desync from the click boxes. `UI.draw_card_select(cards, cursor_index, elapsed, chosen_index)` eases each card in (85%→100% scale, small rise, fade-in) over `CARD_ANIM_DURATION`, staggered `CARD_STAGGER` seconds apart per card index for a left-to-right cascade; when `chosen_index` is set (during `main.lua`'s post-pick confirm delay) the chosen card gets a gold highlight and the other two dim to 35% alpha instead of animating further. The "BOSS INCOMING"/"HAZARD STORM"/"STORM INCOMING" banners (`UI.draw`, priority order boss_active > boss_incoming > storm_active > storm_incoming — all four are mutually exclusive in time by construction in `main.lua`) each pulse via a plain `love.timer.getTime()` sine, no extra per-banner state needed; the active-storm banner flickers noticeably faster (12 vs 6) than the two telegraph banners, since it means "danger right now" rather than "danger soon."
- `src/difficulty.lua` — wave counter + spawn-rate lerp. `Difficulty.wave()` and `Difficulty.skip_wave()` both go through a shared local `wave_at(elapsed)` helper (returns the wave number plus that wave's `[start, end)` boundary) so the two can't drift out of sync — `wave()` just reads the number, `skip_wave()` (the debug hotkey) jumps `elapsed` precisely to the next wave's boundary regardless of how far into the current wave it was. `EARLY_WAVE_DURATIONS` gives waves 1-3 a shorter length than the steady-state `WAVE_DURATION`; `RAMP_WAVES` (used only in `spawn_rate`) is a fixed real-time budget (`RAMP_WAVES * WAVE_DURATION` seconds) for the density ramp, deliberately decoupled from wave *number* so shortening early waves doesn't also warp how fast spawn rates ramp.
- `src/bloom.lua` — render scene to a canvas, bright-pass threshold + separable gaussian blur, additive composite into `Bloom.final_canvas`. **The threshold shader uses max-channel brightness, not perceptual luminance** — perceptual weights (favoring green) unfairly discount saturated reds/blues/purples, so a fully-lit red or purple shape would never bloom under the "correct-looking" luma formula. Keep this in mind when picking colors for new entities (e.g. future boss variants) if you want them to glow.
- `src/hit_effect.lua` — post-processes `Bloom.final_canvas` before it hits the screen: `hit_strength` (decaying, triggered on damage) drives chromatic aberration + vignette; `danger_strength` (continuous, driven by `Player.lives == 1`) drives an independent red-tint pulse. Two separate uniforms so the two effects can stack without fighting.
- `src/high_score.lua` — `love.filesystem` read/write, simple "only overwrite if higher" save.
- `src/cards.lua` — the roguelike layer. `CARD_POOL` (20 defs: `id/name/description/max_stacks/on_pick/modifiers`), `Cards.owned` (stack counts), `Cards.modifiers` (flat table, **fully recomputed from `owned` on every pick** — declarative, not incrementally mutated). `Cards.get(key, default)` is the read API every other module uses. Two cards (Guardian Aura, Regeneration) tick continuously via `Cards.update` and "bank" their trigger — if the condition (shieldless / missing HP) isn't met when the timer completes, it holds at cap and fires the instant the condition becomes true, rather than needing exact timing.
- `src/debug.lua` — F1-toggle overlay + hotkeys; reads `Cards.modifiers`/`Cards.owned` directly for the readout. `Debug.draw` also takes `unlock_stage`/`max_unlock_stage` from `main.lua` (shown as "Unlock stage: X/3" on the state line) purely for visibility while testing the progressive hazard-unlock system — everything else it reads it pulls straight from the modules it already required.

No assets/sprites/audio — everything is drawn procedurally. User explicitly doesn't want music.

### Color palette (avoid clashes when adding new entities)

14. **Boss-type playtest fixes, round 1** (same session as #13, after the user tried it): homing projectiles had no lifetime and would chase the player forever even after the boss left — gave them a 6s expiry. Laser was originally a fixed-pivot rotating ray, which left the area near the boss permanently safe and the far arena permanently threatened — reworked into a full-arena-width horizontal band at a randomized row each cycle, plus one straight (non-homing) aimed shot per cycle. Turret was fully stationary — now orbits circularly around a fixed arena point, and its ring-burst rotates its angle offset a bit more each shot for a spiral pattern. Splitter's shot counts increased (3→6 original, 2→4 clones). Also added **dash invincibility**: `Player.is_dashing` now short-circuits `take_damage` to `"dodged"`, making the Quick Dash/Long Dash cards meaningfully defensive.
15. **Boss-type playtest fixes, round 2**: dash invincibility upgraded from "no damage" to true phase-through — every hazard's collision check now skips outright while dashing (no FX/removal either), not just the damage step; deliberately scoped to hazards only, Orb/VoidOrb pickups stay collectible while dashing since that's beneficial. Homing projectiles now spawn a small green burst FX when their lifetime runs out instead of silently vanishing. The laser's fixed-row band was still static during its firing window — it now slides between two randomized rows over the firing duration, and its aimed projectile shot was moved onto its own independent ~1s timer instead of firing only once per beam cycle, so it shoots noticeably more often. The turret's circular orbit had a one-time "zip" at encounter start (enter-phase landed it at the generic hover point, then hover's orbit formula instantly jumped it to the orbit's own starting position) — fixed by making both the spawn position and the enter-phase target match the orbit formula's angle-0 point for orbiter types, so there's no discontinuity. Also swapped `math.atan2` for a hand-written `atan2` built on single-arg `math.atan`, since `atan2` is removed in standard Lua 5.3+ (still fine on LÖVE's LuaJIT, but this removes the ambiguity for good).
16. **Boss-type playtest fixes, round 3**: the laser's row-slide from round 2 still only covered a small random distance — reworked into a genuine edge-to-edge sweep across the *whole* screen, randomly horizontal (top↔bottom) or vertical (left↔right), each direction equally likely, via `laser_axis` + the two screen edges as start/end. Turret's ring burst now fires twice per volley (~0.18s apart, second ring offset by half the angular spacing to interleave into the first's gaps) via a new generic `pending_second_burst`/`fire_second` mechanism on `Boss`, added specifically for this but reusable by any future type.
17. **Boss-type playtest fixes, round 4**: laser's shared `ENCOUNTER_DURATION` time budget didn't line up with its own beam-cycle length, so it could leave mid-telegraph or cut its last sweep off partway through — replaced with a shot-count exit (`laser_sweep_count >= LASER_MAX_SWEEPS`, set to 4) so it always plays exactly 4 full sweeps before leaving, no more, no fewer. Dropped the telegraph's second (end-position) indicator line — redundant now that every sweep spans a full screen edge to the opposite edge, it was just visual noise. Slowed the sweep down slightly (`LASER_FIRE_DURATION` 2.2s → 2.8s for the same full-screen distance).
18. **Boss-type playtest fixes, round 5**: homing shots could still be alive (mid-flight within their 6s lifetime) when the Homing boss itself left, so its threat could outlive it — added `Projectile.clear_homing()` (explosion-clears every active homing shot) plus a new generic `on_type_exit(type_id)` callback on `Boss`, fired once when any instance's phase flips to `"exit"`; `main.lua` wires it to call `clear_homing()` specifically when `type_id == "homing"`.
19. **Closed a top-camping exploit**: the user found that parking at the very top of the screen made Sentinel and Splitter encounters completely harmless — both bosses only ever fire downward and their bodies never patrol above `HOVER_Y`, so nothing in their kit threatened that space. First fix: an `opts.upward` mode on `fire_spread` (anchors at the boss's top edge, flips `dir_y`) plus a generic `guard_interval`/`guard_fire` hook, giving both bosses a slower upward volley.
20. **The upward-volley fix wasn't enough**: the user immediately found that a fixed-angle fan — upward or otherwise — always leaves *some* position uncovered (corners, in this case), no matter how wide. Replaced the upward `fire_spread` volley with a new shared `fire_aimed_shot` helper that computes a direction toward the player's actual position once at fire time — this can't have a geometric blind spot the way any fixed angle/fan can. Also deduplicated Laser's existing aimed shot (previously its own near-identical local function) onto the same shared helper.
21. **Still not enough — closed top-camping properly**: the aimed shot fixed *coverage* but not the underlying problem — one tracked projectile every ~2s is trivial to sidestep from a fixed spot with nothing else pressuring that position. The user proposed three options (restrict the player's position / make the boss bigger / both); went with both, scoped only to Sentinel and Splitter (+ its clones) per the user's explicit constraint. Added `Player.min_y` (new dynamic lower bound alongside the screen-edge clamp in `Player.bounds()`, drawn as a faint dashed line when raised) and `Boss.get_player_min_y()` (reads an opt-in `type_def.player_min_y`, only set on `sentinel`/`splitter`/`splitter_clone`); `main.lua` writes `Player.min_y` from it every frame, so the wall is automatically only up during those two encounters. Paired with a moderate body-size bump (Sentinel 90x60→125x75, Splitter 65x45→85x55; clones unchanged) so the boss's own patrol has less room to be squeezed past even inside the now-smaller legal zone.
22. **Follow-up pass on the same fix**: extended `Player.min_y` to Homing too (its own shots already steer continuously, but a player camped far enough above still had time to read and juke each one before it curved into range). The aimed "guard" shots on Sentinel/Splitter/splitter_clone were removed outright — with the position denied entirely, out-tracking a player standing there is redundant (Laser keeps its own aimed shot; that one predates the top-camping fix and is unrelated). Also caught and fixed a real bug while re-checking this area: Sentinel/Splitter's `patrol_amplitude` never actually reached the screen edges from their spawn point (off by roughly 100-170px depending on type), so a strip on both sides of the screen was permanently unvisited by the boss's own body regardless of every other fix — corrected both so the patrol genuinely sweeps edge to edge. Projectile counts bumped for more pressure: Sentinel 5→7, Splitter original 6→8, clones 4→6. The clone fix (giving their sine patrol amplitude=820 to reach either edge from any split position) immediately backfired: amplitude directly scales peak velocity, so the clones became absurdly fast, and sine-patrolling both off a shared formula with only a small spawn offset made them drift side-by-side instead of splitting up.
23. **Replaced clone patrol with a real ping-pong bounce**: `splitter_clone` no longer sine-patrols at all. It now moves in a straight line at a constant `bounce_speed` (`is_bouncer`/`bounce_dir`), reversing off the screen edges (same clamp block other types use to stop) and off the other clone via a new `resolve_bouncer_collisions` pass (module-level helper, called once per frame from `Boss.update` after both clones have moved) — direction is set explicitly *away* from the other clone on overlap rather than toggled, so it can't flip-flip while they're still touching. Clones now spawn already moving apart (`Boss.spawn_split_clones` sets one to -1, the other to +1) instead of toward each other.
24. **Splitter (pre-split) was still too fast**: its `patrol_speed` (1.3, unchanged from before the amplitude fix) combined with the corrected wider amplitude (370) gave a much higher peak velocity than intended — slowed to 0.85.
25. **Clones were still launching in the same direction — round 1 fix was incomplete**: clamping only each clone's *final* spawn position (previous entry) still let a clone land exactly on the wall when the split happened near a screen edge. Landing exactly on the wall doesn't fix anything: that clone's very first movement frame still tries to go further outward, immediately hits the edge-clamp, and gets bounced back inward on the spot — same direction as its sibling, before it ever visibly moved apart. Splitter's wide patrol (amplitude 370, needed to actually cover the screen) makes near-edge splits common, so this was hit often, not as a rare corner case.
26. **Real fix**: `Boss.spawn_split_clones` now clamps the *split's reference point* itself (not each clone's final position) into `[offset + buffer, width - clone_width - offset - buffer]` (buffer = 40px) before placing either clone. This guarantees both clones always spawn with genuine clearance to move outward — the left one has room to actually travel left, the right one room to travel right — before either could possibly reach a wall and bounce. After that initial guaranteed run, ordinary wall/each-other bounces take over as normal.
27. **Full-project bug-fix pass**: read every module not already touched this session and fixed six issues found. (1) The "Orbs: X/5" HUD counter was showing the lifetime total against a static /5, so it read "12/5" after the first milestone instead of showing progress toward the next one — now wraps (`src/ui.lua`). (2) `love.on_void_orb_miss` had drifted into a full duplicate of `apply_player_hit`'s dodged/shielded/revived/damaged branches instead of calling it, and in copying it over had silently dropped `Player.flicker_timer` on a normal hit (every other damage source flickers the player, void-orb-miss didn't) *and* was missing the `Player.is_dead`/`GAME_OVER` guard the other four collision handlers all have (meaning a void-orb-miss landing in the same frame as another fatal hit could double-process damage on an already-dead player). Fixed by having it call `apply_player_hit` like everything else — `apply_player_hit` gained optional `death_shake_duration`/`death_shake_magnitude` params (defaulting to the original 0.4/12) so void-orb-miss keeps its own distinct 0.6/20 death shake without needing its own copy of the function. (3) If every one of the 20 cards hits `max_stacks` (only realistic via a very long run or debug F2 spam), `Cards.roll_choices(3)` returns zero cards and `CARD_SELECT` had no escape path — `trigger_card_select` now just skips opening the screen when there's nothing left to offer. (4) `VoidOrb`'s fall speed didn't respect the "Slow Fall" card's `hazard_speed_mult`, even though missing one costs HP the same way touching a hazard does (`Orb`, a pure pickup with no downside, correctly stays unaffected). (5) `Player.min_y` (the top-of-screen wall from #21-22) stayed enforced through a boss's enter/exit phases, not just while it's actually hovering and threatening that space — `Boss.get_player_min_y()` now only counts instances in `"hover"`. (6) The debug overlay's card/modifier summary iterated via `pairs()`, whose order is unspecified in Lua, so the line could visibly reorder between runs — now sorts keys first.
28. **Transition pacing + card-select animation**: playtesting found the normal→boss, boss→card-select, and card-select→normal transitions all snapped instantly with zero breathing room. Added three timers in `main.lua`, all ticked in `love.update`: `boss_incoming_timer` (1.6s telegraph — a pulsing "BOSS INCOMING" banner shows, new hazard spawns are suppressed via `suppress_spawns`, but already-falling ones keep going, so it reads as "things calm down" rather than a hard freeze) before `Boss.spawn` actually fires; `post_boss_pause_timer` (1.0s full freeze, reusing the exact "early `return` skips the rest of this frame" trick `hitstop_timer` already used, just longer) between the boss dying and the card screen opening; `card_confirm_timer` (0.4s) between picking a card and `finish_card_select()` actually resuming play. `trigger_card_select`/`finish_card_select` had to become forward-declared locals so `love.update` (defined earlier in the file) can call them — Lua scopes `local`s by where they appear in the source, not by call order. Also added a cascading scale/fade-in animation to the card-select screen itself (`src/ui.lua`'s `UI.draw_card_select`, staggered per card, layered as a draw-time transform on top of `UI.card_layout()`'s unchanged rects so it can't desync from the click boxes) and a gold-highlight/dim-others treatment while a pick is being confirmed.
29. **New hazard: telegraphed Mine** (`src/mine.lua`) — a deliberately different kind of threat from anything else in the game: the body itself is harmless, only its shockwave deals damage. Falls slowly, anchors at a random height, then arms — a warning ring at its blast radius appears immediately (full telegraph time to route around it) and its bronze core flashes hotter and faster as the ~1.3s countdown runs out. Detonation only damages a player still inside the radius (dash phase-through applies same as every other hazard); the mine removes itself either way. Wired into the normal spawn-rate system (`src/difficulty.lua`'s `mine` config) and suppressed the same way as every other hazard during boss encounters/telegraphs.
30. **Mid-wave hazard storms**: adds rhythm to the wave system beyond its smooth difficulty ramp. Every 2nd wave that isn't also a boss wave, a brief telegraph plays (gameplay unaffected — deliberately the opposite feel from the boss telegraph's spawn-suppression), then a 10s window where Enemy/ZigzagEnemy/Mine spawn ~3x more often via a plain multiplier on their `Difficulty.spawn_rate(...)` call, scheduled the same wave-transition way boss encounters are and explicitly guarded against ever landing on a boss wave. `src/difficulty.lua` itself is untouched — the ramp stays the ramp, storms are a `main.lua`-level event layered on top.
31. **Storms were unsurvivable — narrowed the hazard mix**: speeding up Enemy, ZigzagEnemy, *and* Mine simultaneously stacked every hazard type's density at once, which playtesting immediately confirmed as "hell of a mayhem, almost impossible to live." Fixed not by tuning the multiplier down, but by narrowing what a storm actually *is*: Enemy and Orb both get the 3x rate boost (a red-triangle swarm with more yellow-orb pickups as the reward for braving it), while ZigzagEnemy/Mine/VoidOrb are suppressed entirely for the storm's duration (spawn rate forced to `math.huge`, the same technique `suppress_spawns` already used for boss encounters) instead of also being sped up.
32. **Fixed player draw order**: the Mine's large, opaque, lingering-in-place body made it obvious that overlapping hazards were rendering *on top of* the player — because `Player.draw()` was called first in `love.draw()`, every entity drawn after it (Enemy, ZigzagEnemy, Mine, Orb, VoidOrb, Boss, Projectile) painted over it whenever they overlapped. This wasn't Mine-specific, just most visible there; `Player.draw()` now runs last, after every other entity, so the player is always visually on top regardless of what it's overlapping.
33. **Slowed the boss/storm cadence and bumped the mine's blast radius**: `BOSS_WAVE_INTERVAL` 3→6, `STORM_WAVE_INTERVAL` 2→3 — since 6 is a multiple of 3, storms and bosses now alternate cleanly every 3 waves with no gaps and no collisions, instead of occasionally landing on the same wave. Also bumped Mine's `BLAST_RADIUS` 70→90.
34. **Progressive hazard unlocks**: previously every hazard/pickup type was live from wave 1, with only the spawn *rate* ramping over time — variety and pace were conflated into one axis. Added `unlock_stage` (0-3) so the roster itself grows one event at a time instead: only Enemy/Orb from the start, then VoidOrb/ZigzagEnemy/Mine each wait for their own threshold, incremented once per boss defeated or storm survived (checked at the moment each concludes, not when it starts). Reuses the exact `math.huge`-spawn-rate suppression technique `suppress_spawns`/`storm_active` already used, just gated by a new condition rather than a new mechanism. Added an "Unlock stage: X/3" readout to the debug overlay for visibility while testing this.
35. **Graduated early wave durations**: the user's real ask, after a round of miscommunication (first read as "score needed to complete a wave," which doesn't exist — waves are pure time), was "the early game feels boring, waves should complete faster there." A flat `WAVE_DURATION` cut would've sped up the *whole* run, not specifically the early game, so instead waves 1-3 got their own shorter lengths (10s/13s/16s vs. the steady 20s from wave 4 on) via a new `EARLY_WAVE_DURATIONS` table. `Difficulty.wave()` and `Difficulty.skip_wave()` were rewritten around a shared `wave_at(elapsed)` helper so both stay in sync. Since boss/storm cadence is wave-*number*-gated, this has the nice side effect of pulling the first storm and first boss noticeably earlier in real time too (first storm ~t=23s instead of ~t=60s, first boss ~t=79s instead of ~t=120s) without touching the density ramp's own timing (`RAMP_WAVES * WAVE_DURATION` stays a fixed 120-second real-time budget, deliberately decoupled from wave number).
